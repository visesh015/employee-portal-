# Database Migration Versions

## 1. What Is This Folder?

The storage directory for all linear Alembic migration revision script files.

## 2. Why Do We Need It?

It preserves the complete historical sequence of database schema changes over the lifecycle of the project.

## 3. Main Responsibility

Storing version-controlled Python migration scripts that implement `upgrade()` and `downgrade()` functions.

## 4. How It Works

Each migration script represents an atomic schema increment. Scripts form a directed acyclic graph (typically a single linear chain) linked by `down_revision` pointers. Alembic executes scripts in sequence to bring any database up to date.

## 7. Allowed Responsibilities

Versioned migration revision files generated by Alembic or manually authored.

## 8. Boundaries

- Must not contain application source code.
- Individual migration files must not be altered once applied to shared environments (DEV, QA, UAT, Prod).

## 9. Connection With Other Layers

- Called by: Alembic migration runner (`env.py`).
- Calls: SQLAlchemy schema DDL operations.

## 10. Data Flow

Enters: Revision commands. Leaves: DDL operations applied to the database.

## 11. Validation Responsibility

Alembic validates that revision chains have no broken parent links or circular heads.

## 12. Authentication and Authorization

No security decisions.

## 13. Error Handling

DDL errors cause the specific migration script to abort.

## 14. Transaction Responsibility

Each script executes within a database transaction.

## 15. Logging and Auditing

Tracked via the `alembic_version` table in PostgreSQL.

## 16. Naming Convention

Files: `<revision_id>_<slug>.py` (e.g. `20261123_create_attendance_tables.py`).

## 17. When to Add a New File

Whenever a model is added, modified, or deleted in any module.

## 18. Common Mistakes

- Creating branching heads in migrations without merging them.
- Committing destructive drop-column operations without deprecation periods.
